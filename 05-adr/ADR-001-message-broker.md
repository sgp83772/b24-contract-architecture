# ADR-001: Выбор брокера сообщений для интеграции с 1С

**Статус:** Принято
**Дата:** 2026-11-02
**Контекст принятия:** проектирование интеграции Bitrix24 ↔ 1С:УПП

## Контекст
При создании платежа в портале Bitrix24 информация должна попасть в 1С:УПП. Прямой вызов REST API из Bitrix24 в 1С создаёт жёсткую связность: если 1С недоступна (обновление, регламентные работы), платёж не передаётся, а повторная отправка вручную приводит к дублям.

## Проблема
Как обеспечить гарантированную доставку платёжных событий из Bitrix24 в 1С без потерь и без дублей, не блокируя работу менеджеров в портале?

## Рассмотренные варианты

### Вариант 1. Прямой REST-вызов B24 → 1С
- **Плюсы:** минимум компонентов, быстро внедрить.
- **Минусы:** нет буфера при недоступности 1С; нет ретраев; нет DLQ; дубли при ручном повторе; логика ошибок размазана по коду Bitrix24.

### Вариант 2. RabbitMQ
- **Плюсы:** гарантированная доставка (persistent + publisher confirms); DLQ; ретраи; зрелый, легко эксплуатируется; есть Management UI.
- **Минусы:** ещё один компонент в ландшафте; нужен мониторинг.

### Вариант 3. Apache Kafka
- **Плюсы:** горизонтальное масштабирование; хранение истории событий.
- **Минусы:** избыточен для 50 сообщений/сек; сложнее эксплуатация (ZooKeeper/KRaft, partitioning, consumer groups); нет DLQ из коробки (надо руками).

## Решение
Выбран **RabbitMQ**.

## Обоснование
Объём событий (50/сек, пик 200/сек) не требует Kafka. RabbitMQ проще в эксплуатации, даёт из коробки DLQ и retry-логику, покрывает все сценарии обмена с 1С и телефонией.

## Последствия
**Положительные:**
- Платежи не теряются при падении 1С.
- Единая точка наблюдаемости (Management UI).
- Асинхронность разгружает портал.

**Отрицательные:**
- Нужен мониторинг очередей и DLQ.
- Появляется ещё одна инфраструктурная единица (небольшие затраты на DevOps).
