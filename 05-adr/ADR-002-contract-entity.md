# ADR-002: Реализация сущности «Договор» как смарт-процесса

**Статус:** Принято
**Дата:** 2026-11-02

## Контекст
В компании «Альфа-Строй» жизненный цикл договора включает 8 стадий: подготовка → согласование → подписание → исполнение → закрытие → архив → расторжение → претензионная работа. С договором связаны: спецификации, счета, акты, платежи, задачи согласования, версии документов, претензии. Нужен отдельный набор полей (номер, дата, сумма, тип, дата начала/окончания), права доступа по ролям и связь с CRM-компанией (контрагент).

## Проблема
Как реализовать договор в Bitrix24, чтобы поддерживать его жизненный цикл, кастомные поля и связи с 7+ сущностями?

## Рассмотренные варианты

### Вариант 1. Сделка (стандартная CRM)
- **Плюсы:** «из коробки», есть воронка стадий.
- **Минусы:** сделка — про продажу; поля заточены под лид/сделку; смешивание с воронкой продаж; права доступа не гибкие; нельзя привязать свои стадии без «насилия» над CRM.

### Вариант 2. Инфоблок
- **Плюсы:** гибкие поля.
- **Минусы:** нет стадий/канбана; нет штатных прав по ролям; слабая интеграция с CRM; придётся писать модуль для UI.

### Вариант 3. Смарт-процесс
- **Плюсы:** своя воронка стадий; кастомные поля; права по ролям; связь с CRM-компанией; штатный UI (канбан, список, карточка); бизнес-процессы из коробки.
- **Минусы:** ограничение на число смарт-процессов (зависит от лицензии); чуть меньше гибкости, чем у инфоблока.

## Решение
Выбран **смарт-процесс**.

## Последствия
**Положительные:**
- Отдельная воронка стадий под жизненный цикл договора.
- Штатные права по ролям (юрист, финансист, менеджер).
- Связи с компанией, счетами, актами — через штатные поля связей.

**Отрицательные:**
- Кастомные стадии нужно настраивать отдельно (в ADR не входит — это конфигурация).
- Ограничение по количеству смарт-процессов в лицензии — учитываем при проектировании (у нас 6 смарт-процессов, влезаем).
