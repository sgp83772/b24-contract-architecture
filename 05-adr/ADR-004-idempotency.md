# ADR-004: Обеспечение идемпотентности при повторных вызовах из 1С

**Статус:** Принято
**Дата:** 2026-11-02

## Контекст
1С отправляет в Bitrix24 события (договор создан/обновлён, счёт, платёж) через webhook. Сеть нестабильна, 1С ретраит при таймаутах. Без защиты повторный вызов создаст дубли договоров и платежей.

## Проблема
Как гарантировать, что повторный вызов с тем же содержимым не создаст дубль, но при этом не заблокирует реальное обновление (например, смену статуса через минуту)?

## Рассмотренные варианты

### Вариант 1. Проверка по номеру договора
- **Плюсы:** просто.
- **Минусы:** номер может быть пустым (черновики); не работает для платежей и счетов.

### Вариант 2. Уникальный индекс в MySQL
- **Плюсы:** железно.
- **Минусы:** нужна миграция схемы; Bitrix24 не даёт свободно менять индексы смарт-процессов.

### Вариант 3. Ключ идемпотентности в Redis
- **Плюсы:** не трогаем схему Bitrix24; гибко настраивается TTL; легко масштабируется.
- **Минусы:** Redis — ещё один компонент; при падении Redis без persistence возможна потеря ключей.

## Решение
Выбран **Redis с TTL 24 часа**.

## Формат ключа
`idempotency:{entity}:{external_id}:{updated_at}`

Пример: `idempotency:contract:1C-2026-0042:2026-11-02T10:15:00Z`

## Логика
1. Адаптер получает запрос из 1С.
2. Формирует ключ из `entity`, `external_id`, `updated_at`.
3. `SET key 1 NX EX 86400` (24 часа).
4. Если SET вернул OK — обрабатываем.
5. Если SET вернул nil (ключ уже есть) — возвращаем `{"skipped": true}` с HTTP 200.

## Последствия
**Положительные:**
- Дубли исключены.
- Схема Bitrix24 не меняется.
- TTL 24 часа покрывает все ретраи 1С.

**Отрицательные:**
- Нужен Redis (persistence AOF включён).
- Если 1С повторно отправит **реальное изменение** с тем же `updated_at` в течение 24 часов — оно будет проигнорировано (приемлемо: 1С всегда обновляет `updated_at` при изменении).
