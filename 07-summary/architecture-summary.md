# Architecture Summary — Портал договоров на Bitrix24

## Контекст
ООО «Альфа-Строй», 200 сотрудников, строительный подрядчик. Договорный документооборот ведётся в Excel и почте, данные по платежам расходятся с 1С. Цель портала: единая точка работы с договором — от согласования до закрытия.

## Три ключевых архитектурных вызова

### 1. Связность Bitrix24 ↔ 1С
Прямой синхронный вызов REST при недоступности 1С блокирует работу менеджеров и создаёт дубли.
**Решение:** асинхронный обмен через RabbitMQ + ретраи + DLQ + идемпотентность (ADR-001, ADR-004).

### 2. Модель данных под жизненный цикл договора
Сделка и инфоблок не покрывают 8 стадий, права по ролям и связи с 7 сущностями.
**Решение:** договор и связанные сущности — смарт-процессы; версии файлов — HL-блок + S3 (ADR-002, ADR-003).

### 3. Объём файлов и бэкапов
60 000 файлов × 5 МБ ≈ 300 ГБ. Хранение в MySQL раздувает бэкапы и замедляет восстановление.
**Решение:** файлы в S3, метаданные в HL-блоке (ADR-003).

## Принятые решения (сводка)
| # | Решение | Почему |
|---|---|---|
| 1 | Договор — смарт-процесс | Свои стадии, права, связи с CRM |
| 2 | Обмен платежами — через RabbitMQ | Буфер, ретраи, DLQ |
| 3 | Версии файлов — HL-блок + S3 | Не раздувать MySQL, хранить историю |
| 4 | Идемпотентность — Redis TTL 24ч | Защита от дублей при ретраях 1С |

## Ожидаемый эффект
- Задержка синхронизации договора из 1С — не более 5 минут.
- Ноль потерь платежей при падениях 1С.
- Бэкапы MySQL сокращаются в 10+ раз (файлы вынесены в S3).
- Единая точка работы с договором для юриста, менеджера и финансиста.

## Границы проекта (что не входит)
- Реализация и настройка Bitrix24 (это архитектура, не внедрение).
- Миграция исторических данных.
- Обучение пользователей.
- Дизайн UI/UX.
